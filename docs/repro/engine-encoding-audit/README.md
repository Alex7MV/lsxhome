# Аудит кодировки: logestix vs. lsxhome (MVP чата)

Цель: воспроизвести в проекте движка то, что заставило GUI-оболочку
(lsxhome) добавить собственный фильтр `NormalizeEngineText`.

## Что наблюдается в lsxhome (эталонные факты)

Модель: `gemma-4-26B-A4B-it`, конвертированная движком
(`<model>/logestix/pinned/tokenizer_vocab.arrow`, `tokenizer_merges.arrow`).

1. **В ответе модели встречаются байты, не образующие UTF-8** (`C2 97` = U+0097,
   повторяющиеся десятки раз), а также символы, которых не было в вопросе.
2. **Из-за этого ломается следующий вопрос.** Ответ попадает в историю и
   кодируется обратно через `arrow_tokenizer_encode`; одиночный байт без
   ведущего даёт `rc=-1` → `BuildConversationInputIds` возвращает false → вопрос
   не отправляется («первый вопрос работает, второй нет»).
3. **Модель жалуется на кодировку** («the wrong encoding», «C with a dot above»)
   притом, что её собственный ответ содержит эти символы.
4. **Пробелы в ответе выглядят как `C4 A0`.** Проба показала, что это не
   vocab-маркер, а два byte-fallback куска `<0xC4><0xA0>`; такой текст движок
   кодирует и декодирует без проблем.

Что **не** является причиной (проверено побайтово):

- текст из окна приложения приходит в движок корректным UTF-8
  (`D0 9F D1 80 …` = «Привет»), конвертация по `GetACP()` его бы испортила;
- «U+00A0 (NBSP)» и «маркер пробела Ġ» — не то, что происходит: первое никогда
  не появлялось, второе в словаре отсутствует.

## Что уже измерено пробой (гема-4-26B-A4B-it)

Прогон `tokenizer_audit` на конвертированном чекпойнте даёт:

```
vocab_size=262144 tokenizer_kind=0 byte_fallback=0 add_dummy_prefix=1 escape_whitespaces=1 merges=385685

[ ok ] vocab stores the space as a plain 0x20 token               id=236743
[FAIL] vocab lifts bytes into U+0100..U+0143 (GPT-2 style)        id=-1
[ ok ] decode(space) yields a plain space                         decoded=[ ]
entries: byte-fallback=256 lifted(C4 xx)=0 C1-controls(C2 8x..9x)=22
[ ok ] encode plain ASCII                                         rc=3
[ ok ] encode cyrillic UTF-8                                      rc=13
[ ok ] encode U+0120 (the 'Ġ' glyph seen in answers)             rc=3
[ ok ] encode a C1 control (U+0097)                               rc=5
[FAIL] encode a lone continuation byte (0x97)                     rc=-1
[FAIL] encode a lone lead byte (0xC4)                             rc=-1
byte_to_token_id populated for 256/256 bytes
```

Что из этого следует (важно для аудита — часть ранних гипотез **опровергнута**):

1. **«Маркер пробела Ġ (U+0120) в словаре отсутствует.** В этой модели пробел —
   обычный одно��айтовый токен, `decode` даёт настоящий пробел. GPT-2-подобного
   подъёма байтов в `U+0100..U+0143` нет вообще (`lifted = 0`).
2. **Символ `C4 A0` в ответах модели — это не vocab-маркер, а байты**, собранные
   моделью из byte-fallback кусков `<0xC4><0xA0>`; такой текст кодируется и
   декодируется без проблем (`rc=3`).
3. **Механизм отказа найден однозначно:** любой одиночный байт, не начинающий
   UTF-8-последовательность (`0x97`, `0xC4`), даёт `arrow_tokenizer_encode` →
   `rc=-1`. Модель такие байты выдаёт (в ответах повторяются `C2 97` = U+0097,
   в словаре 22 C1-управляющих), и один такой байт в ответе убивает весь
   следующий промпт: `BuildConversationInputIds` возвращает false.
4. **`byte_to_token_id` заполнен для всех 256 байт**, `byte_fallback=0` — то есть
   кодировщик допускает любые байты, а декодировщик отдаёт их как есть.

**Вопросы к движку:**

- должен ли `arrow_tokenizer_decode` (ветка `tokenizer_kind == 0`) отбрасывать
  или экранировать байты, не образующие корректный UTF-8, чтобы ответ всегда был
  валидным текстом?
- где правильнее фильтровать: в декодере, в `IncrementalDetokenizer` или в
  конвертере (запретить byte-fallback куски, из которых модель собирает мусор)?
- нужно ли при обратном кодировании отвечать «мягко» (заменять невалидный байт на
  replacement char), а не отклонять весь промпт?

## Проверка без GPU: `tokenizer_audit.cpp`

Самодостаточная утилита: нужны только `lsxcommon` и Arrow, **модель не
грузится, CUDA не нужна**.

## Сборка зонда

В этом репозитории зонд — обычная цель CMake (не часть тестов):

```powershell
cmake --preset windows-debug
cmake --build --preset windows-debug --target tokenizer_audit
.\build\windows-debug\bin\Debug\tokenizer_audit.exe D:\path\to\model-root
```

Аргумент — корень модели (каталог, внутри которого лежит `logestix/pinned/`).

Сборка внутри проекта движка — та же строка компиляции, что и выше, плюс
линковка `lsxcommon`, `arrow_shared` и absl-библиотек, на которые он ссылается
(`absl::flat_hash_map`, `absl::span`, `absl::strings`); удобнее всего добавить
цель в его CMake и собрать через `cmake --build . --target tokenizer_audit`.

Код возврата: `0` — всё чисто, `1` — есть расхождения, `2` — не открылся словарь.

Что она проверяет (каждая строка `[ ok ]` / `[FAIL]`):

| Проверка | Ожидание | Что означает `FAIL` |
|---|---|---|
| пробел — обычный токен `0x20`, `decode` даёт пробел | `ok` | декодер и словарь искажают базовый текст |
| в словаре есть подъём байтов в `U+0100..U+0143` | зависит от модели | для этой модели `absent` — GPT-2-теория неприменима |
| `decode`/`encode` ASCII и кириллицы | `rc>=0`, round-trip | базовая токенизация сломана |
| `encode` одиночного `0x97` / `0xC4` | `rc<0` | **подтверждает причину падения фрейминга** |
| `encode` C1-управляющего `U+0097` | `rc>=0` | в словаре есть куски, которые модель выдаёт как мусор |

Код возврата: `0` — всё чисто, `1` — есть расхождения, `2` — не открылся словарь.

**Главный вопрос аудита:** должен ли `arrow_tokenizer_decode` (ветка
`tokenizer_kind == 0`, byte-level BPE) разворачивать GPT-2 `bytes_to_unicode`
обратно в байты? Если да — где это правильнее сделать: в декодере или в
`IncrementalDetokenizer`? Сейчас разворот делает вызывающая сторона, потому что
в движке этого нет.

## Проверка с моделью: сценарий промптов

Запуск (любой из движковых CLI, умеющих multi-turn):

```bash
# lsxbenchmark / lsxfabric / lsxcli — модель одна и та же
--model /path/to/gemma-4-26B-A4B-it
```

Промпты — **в этом порядке**, каждый следующий имеет значение:

1. `Привет!`
2. `Как дела?`
3. `Привет, как дела?`
4. `Ответь одним предложением про небо.`
5. `Скинь список из трёх пунктов.`

Что смотреть в логе (`--log`):

* `[gemma-infer]` / `arrow_tokenizer_decode` — в ответе идут `C4 A0` вместо
  пробелов, а после кириллицы — повторы `C2 97`;
* при `BuildConversationInputIds` на втором и последующих ходах — ошибка
  кодирования (в lsxhome это `failed to frame the prompt for the model`);
* ответы на вопросы 1–3 содержат «неправильная кодировка», «C with a dot
  above» и другие символы, которых не было в вопросе.

Дополнительно (полезно для аудита конвертации): сверить `tokenizer.json`
модели с `logestix/pinned/tokenizer_vocab.arrow` — есть ли расхождения в
представлении непечатных байт и в наборе byte-fallback кусков.
